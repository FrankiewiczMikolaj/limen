# Team-2 critique of team-1 and team-3 (round 2)

This critique checks both draft proposals against `src/job/task-note.ts`, `test/u14-task-note.test.ts`, the code that writes and carries job files, and `/Users/overment/Downloads/limen-note-examples-data/examples.json`. It does not rewrite the team-2 proposal. Effectiveness is unproven for all three drafts; neither study found a clear effect.

Checks run: a script compared each team's three old-note excerpts with the `note` fields in `examples.json` (all three match verbatim for both teams); line counts were counted in both FORMAT blocks; the code claims below were read in the current worktree.

## Team-1 (`group/proposals/team-1.md`, commit `e605d59`)

### What is right

- **The Miss line stays open until it has its own evidence.** This is the strongest single rule in either draft. "An End check with evidence does not clear Miss" closes the exact failure where the main outcome passes and a restriction was broken. Keep it in any final text.
- **No evidence is stored in the note.** Crossing off removes an Open line; evidence is named once, in the final message. This answers the "evidence becomes a result log" tension better than a proof clause per check, and the draft names its cost: the note alone does not show why a line left Open.
- **The marker grammar survives.** 🔴, 🟡, and ⚪ keep their current meanings, narrowed. The `changed` line keeps the exact literal `"🟡 changed: ... Reason: ..."` that the current code uses (`src/job/task-note.ts` line 10) and that the test fixture uses (`test/u14-task-note.test.ts` lines 34, 49). A reader who scans for that line keeps working.
- **String hygiene matches the tested contract.** The no-reminders `noteStart` and `noteSteer` contain no "reminder", which is not cosmetic: the current test asserts the no-reminders first prompt does not match `/reminder/i` (`test/u14-task-note.test.ts` line 28). The clauses also keep the current order in `noteCheck` (note now, first note, reminders, mark sentence, finish-tool sentence; `src/job/task-note.ts` lines 41-56).
- **The carried-note classification rule is new and useful.** Sorting a predecessor's 🟡 lines into "states a restriction or a later check" (keep) against "says what already happened" (result) gives a continued agent a decision it can apply line by line. Example 8's work-order limit is the right test case for it.

### What is wrong, with evidence

- **"About six lines" is only true at the minimum.** FORMAT requires one Miss line, two to four End lines, and one Open line for the Miss and for each End check: six lines at the smallest task, ten at the stated maximum, before any `changed` line or ⚪ line. The draft's own FORMAT example is seven lines for two End checks. The three rewritten examples hit six only because each has exactly two End checks. Any real task with four end checks breaks the shape the brief asked for, and the draft does not say which part gives way.
- **The FORMAT example contradicts itself.** The second End line already states "The stated limit is 60 requests per minute", and its `changed` line then says "the limit is 60 requests per minute. Reason: the owner steered." Nothing changed. The current code's example has the limit at 100 in the main line and 60 in the changed line (`src/job/task-note.ts` lines 15-18); team-1 copied the changed value into the main line. An agent copying this example learns that a `changed` line can restate its parent, which is the log behaviour the draft forbids.
- **Open duplicates every check, and `noteCheck` then double-counts it.** The mark sentence says "mark each 🔴 point". Miss, End, and Open lines are all 🔴 points, so each check appears twice in the finish accounting, and removing an Open line after evidence reads as a 🔴 point that vanished. The draft's defence ("deleting an End line without evidence is dropped") does not cover deleting an Open line, which is the normal, rewarded act. Short Open names also drift: the draft says they are "short names, not a second full copy", yet its example Open lines repeat the End wording almost exactly ("the 101st request is rejected" under "A new key is rejected on the 101st request"). Two copies that must be edited together, by prose instruction only in `noteSteer`, will drift.
- **Coverage past four checks is dropped by design, and too late.** The tension section says a further bullet "goes under Miss, or the Note check marks it dropped". A bullet that fits neither Miss nor the four End lines is therefore discovered as dropped at the finish, after the work. The brief requires exact limits and restrictions to be kept when they define acceptance. Marking a restriction dropped at the finish is an admission, not coverage. Example 3 in the full record has five checks; the draft's shape cannot hold them without this failure.
- **`See:` names no proof a person can repeat.** FORMAT's End lines require "what a person can run or see", but the examples give "See: the rejection" and "See: both files". There is no command, file, or output named, and no place where the evidence lives. Combined with "do not write the evidence here", a crossed-off check is auditable only through the final message. If that message omits a name, nothing in the note or the first-note comparison can catch it, because Open lines were deleted rather than marked.
- **Deleting predecessor result lines can delete the warning the result produced.** `noteStart` tells a continued agent to delete result lines. In example 3's source family, the most useful line is a gap found by a result ("No permanent test sends a forged approval through either gate"). It states no restriction and no later check, so the classification deletes it from the working note. The draft's example 8 reasoning keeps the work-order limit only because it happens to be phrased as a future check; a gap phrased as a finding is lost. The first-note copy does not save it: `recordNote` keeps only the first version ever seen (`src/job/task-note.ts` lines 59-69), and a continued job carries the parent's `note.md` and `note.first.md` (`src/commands/continue.ts` lines 434-440), so the parent's final note is exactly the file being edited down.
- **A ⚪ assumption can carry acceptance risk and is never on Open.** The FORMAT example ends with "Assume the proof uses a test key, not a customer key." If that assumption is false, the proof is invalid, yet no Open line tracks it and the finish check never asks about ⚪ lines. The draft narrowed 🟡 but left ⚪ as a free line that can hold an untested premise.
- **Example 1 garbles a limit name.** The new note says "the cargo plant prepare stall limit and the cargo plant tool stall limit". The source names two limits, the prepare limit and the tool stall limit. "Prepare stall limit" merges them. In a note whose value is exact limits, a merged name is a wrong check. Its one Miss line also folds in "no other limit moved" from the word "Just", which the draft admits is a reading, not a quoted sentence; that reading then sits in the note with the same weight as the quoted clock rule.
- **The reminders steer is still unactionable, as in the current code.** With reminders, the agent must "add a line under that point in {jobDir}/note.md" when a steer changes a project reminder, but the reminder point is not in `note.md`. This is inherited wording, not a new fault, but the draft claims the obligations are kept without noting that this one cannot be followed as written.

### What could still be missed under team-1

A task with two independent hard boundaries where neither is "the" miss; a fifth acceptance bullet; an assumption that invalidates a proof; a predecessor finding phrased as a result rather than a future check; and any check whose `See:` pointer is too vague to repeat.

### What I would keep from team-1

The Miss rule with its own Open life; no evidence stored in the note; the unchanged markers and `changed` literal; the clause order in `noteCheck`; and the restriction-versus-result classification for carried notes, with one change I would argue for in the final round: delete a result line only after its consequence, if it has one, is written as a check or a restriction.

## Team-3 (`group/proposals/team-3.md`, commit `e0ae51d`)

### What is right

- **Unticked means not proven, with no second list.** This removes team-1's duplication problem at the root. One copy of each check cannot drift against itself, and the finish check can still name every unticked line as not proven. It is the cleanest answer to the brief's third part.
- **The stale-proof rule on steer is the best steering sentence in either draft.** "Untick a check whose proof the steer made stale" handles changed scope mechanically: the agent does not judge whether the old proof feels close enough. Keep it, in whatever final shape.
- **Two code claims check out.** Every published job folder does get a `task.md` (`src/job/publication.ts` line 102, `"task.md": job.task`), so taking the checks from the task file instead of "from memory" is grounded. A continued job does carry both `note.md` and `note.first.md` from its parent (`src/commands/continue.ts` lines 434-440), so the `[F]` label about an earlier job is accurate. The FORMAT growth claim is also accurate: the block is 14 lines against the current 9 (counted).
- **`(not run: <reason>)` is the right shape for a forbidden or impossible check.** It keeps the check visible, gives the reason at the finish, and both FORMAT and `noteCheck` state that the note never permits a forbidden run.
- **Gone-line accounting.** When the first note differs, each line that is gone gets its own line at the finish. The current text shows both notes but never requires accounting for a vanished point; this does, and it is the only proposed guard against silent dropping that works at the level of lines.
- **All three old notes are verbatim**, and the new notes are plans. The script check passed for team-3 as for team-1.

### What is wrong, with evidence

- **The reminders instructions contradict each other.** `noteStart` says "do not copy them into the note", because the finish check asks about each 🔴 reminder. `noteSteer` variant `[R]` then says, for a changed reminder, "copy its line into the note first". A copied reminder line is then a check in the note and also a 🔴 reminder, so `noteCheck` `[R]` counts it twice: once as a check, once as a reminder. The agent cannot follow both strings. One of them must change; as written, the steer case, which is the case that matters, breaks the start case.
- **"Quote the task's words" and "Do not copy the task" stand in the same FORMAT.** Line 3 requires the task's words for the easy-to-miss rule; line 5 forbids copying the task. The intended reading (quote one rule, copy nothing else) is not stated, and the examples quote prohibitions word for word. An agent resolving the contradiction toward quoting gets a note of quoted rules; toward not copying, it paraphrases the one rule where exact words carry the boundary. This invites the task-copy failure the brief names.
- **Done-when checks do not name their proof in advance.** FORMAT asks for the proof method only on the Easy-to-miss line. A Done-when line names its proof only after the work, as `(seen: …)` on the tick. The central question asks what must be true at the end and how the agent will prove it; for two to four of the three-to-five lines, the "how" is written after the evidence exists, which is when a weak proof is easiest to accept. Team-1's `See:` is too vague, but it at least forces the pointer to exist at plan time. Team-3 forces it only at tick time.
- **The pointer check defers the whole acceptance list to the finish.** "Write one check that points to that list; do not copy it" keeps the note short by keeping the actual checks out of it. During the work, the note shows one line where eight obligations sit behind a pointer; the agent must re-open the task file to see them, which is the task-copy problem inverted. Worse, `noteCheck` expands the pointer into one line per item only at the finish. A missed item is therefore found at the finish, not during the work. That is the same late-discovery fault as team-1's dropped bullet, with a cleaner surface.
- **`noteCheck` invites running checks at the finish.** "If the task allows it, you may still prove an open check now" arrives at the one moment when a second run is most tempting and least visible. Two supplied examples (2 and 4) bind the agent to run a named check exactly once or to run no other check. The next sentence ("Never run a check that the task forbids") does not cover "run once" tasks: a finish-time run is allowed by the task and still breaches the count. The continued-job study also counted rerunning a passed check as a cost. This sentence should not survive into a final text.
- **The `changed` line loses its marker, and one justification for a loss is wrong.** The current literal is `"🟡 changed: ... Reason: ..."` (`src/job/task-note.ts` line 10), used in the test fixture and in every note a coordinator reads. Team-3 drops the 🟡. No runtime parser reads that marker (the file's own comment says Limen "never parses" the notes), so this is a reader-convention break, not a code break, and the draft should say so plainly instead of folding it into "markers dropped on purpose". Separately, dropping "add a time only when it helps" is justified by "`recordNote` already records each note change with a time". That log line records when the note changed (`src/job/task-note.ts` lines 59-69). It cannot hold a time that is content, such as a due date or a "by 14:05" in the current example. The justification proves the wrong thing.
- **Rewriting an earlier note is weaker than the continued-job problem.** `noteStart` says "If the note was written for an earlier task, rewrite it for this one." A continued job usually extends the same task; a note written for the same task with added scope is not "written for an earlier task", so the rewrite instruction does not fire, and a note written for an earlier task gets rewritten with no instruction to keep points that still bind. Team-1's classification rule handles both cases line by line. Team-3's `[F]` gone-line accounting catches a dropped line only at the finish, after the work that needed it.
- **Two example checks can be ticked while the property fails.** Example 3: "Each place that sets the resolver is host code, or the review names each place that is not." Naming a non-host setter ticks the check while the trust property is broken; the check measures review completeness, not the boundary. Example 8: "The final message gives the new numbers" is a check about the final message, written in a note that must be ticked before that message exists. Both blur a check a person can run or see at the end into a check about the report.
- **The FORMAT example teaches a generic command.** Its third Done-when line is "`npm test` passes." A supplied-shape example with a blanket test command invites agents to add it to notes where the task named a narrower check, or forbade others. The brief requires exact commands only where they define acceptance; a stock line in the example works against that.

### What could still be missed under team-3

Any item behind a pointer check until the finish; a restriction in a carried note that is neither a check nor the one easy-to-miss rule; a proof method for a Done-when check, chosen after the evidence; a "run once" limit, breached by a well-meant finish-time proof; and a changed reminder, where the draft tells the agent two opposite things.

### What I would keep from team-3

The single unticked list as the not-proven state; unticking a stale proof on steer; `(not run: <reason>)`; gone-line accounting when the first note differs; "proven needs named evidence" as the finish vocabulary; and the task file, not memory, as the source when no note exists.

## Where the two drafts agree, and where the final round must decide

Both drafts name one easy-to-miss rule, keep results out of the note, refuse to treat unknown as passed, keep the finish-tool sentence conditional, propose no parser or gate, and claim no delivery benefit. Their real disagreement is where the not-proven state lives: team-1 duplicates each check into an Open list and deletes from it; team-3 keeps one list and ticks it. Duplication drifts; ticking can be misread as "done" rather than "proven", which team-3 itself names as unguarded except by one word in `noteCheck`.

Two decisions for the final round:

1. Take team-3's single list and team-1's rule that the easy-to-miss line needs its own evidence, or take team-1's Open list and accept the drift cost. Keeping both mechanisms reintroduces two states for one fact.
2. Decide where proof is named: at plan time, at tick time, or only in the final message. Team-1 names a vague pointer early and the evidence late; team-3 names a pointer at the tick and the evidence late. Neither names, at plan time, a proof a person could repeat. That is the gap a final text should close, within the line budget both drafts strain against.

No route failed in round 1. Team-1 used `pi:xai/grok-4.7:high`, team-3 used `pi:pi-claude/claude-opus-5-5:xhigh`, and both committed only their proposal file, as the brief required.
